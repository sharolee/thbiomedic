## 1. 背景

广州天泓医疗科技有限公司现有企业站（`https://www.thbiomedic.com`，中文 `/zn/`、英文根目录）基于万户 ezEip CMS + ASP.NET（`.aspx`），前端为 jQuery 3.3.1 + Slick/Swiper，全站 title 无页面级差异化、无 sitemap、静态资源防盗链。项目要求**全面重做**为「先进、美观、内容完整」的中英文双语企业官网，使用 HTML 与各项先进前端技术。

以 W1-B 内容盘点（`docs/content-inventory.md`）为事实基线，新版需要承载的内容特征如下：

| 特征 | 事实（来自盘点） | 对选型的含义 |
|---|---|---|
| 页面规模 | 中文站 64 页 / 英文站 68 页；主栏目 6 个（首页/关于/产品/资源/新闻/联系） | 页面量中等，**模板化程度高**（列表页/详情页高度同构） |
| 产品结构 | 10 个一级分类 + 17 个二级分类 + 每语言 12 个产品详情页 | 适合「数据 + 模板」驱动生成，而非逐页手写 |
| 双语 | 中英一一对应，lcid 同构；有「空分类」（15/17 二级分类无产品） | 需要**语言无关的内容模型** + 路由级语言分区 |
| 媒体 | 119 个图片资源、27 个视频 MP4、6 个 PDF | 需要静态资源管线（压缩、转码、懒加载） |
| 交互 | 轮播、荣誉证书灯箱、视频播放、站内搜索、在线留言表单 | 需要少量**岛式**交互组件，非全站 SPA |
| 表单 | 全站通用「在线留言 / Feedback」表单 | 表单后端方案需独立决策（本 ADR 只定前端边界） |
| 现状工程 | 全新空目录，无既有 CI、无远端仓库 | 技术栈可自由选择，无历史包袱 |

**核心结论（决策驱动）**：这是一个**内容驱动、以静态展示为主、交互点少、多语言**的营销型企业站。它**不是** Web 应用（无登录、无用户数据、无服务端业务逻辑）。选型应优先服务：内容可维护性、多语言能力、SEO、性能与视觉表现力，而非应用开发范式。

## 2. 约束

| 类别 | 约束 | 来源 |
|---|---|---|
| 交付形态 | 需产出**可运行的站点源码**，本地能起服务、能构建；部署目标未定 | SHAR-18 交付定义 |
| 技术方向 | 必须使用 HTML + 现代前端技术 | 项目描述 |
| 双语 | 每页中英双语，内容一一对应，无未翻译占位 | SHAR-18 交付定义 |
| 内容完整 | 以 W1-B 盘点清单为准逐项可核对 | SHAR-18 交付定义 |
| 视觉 | 先进、美观，需通过视觉验收（截图比对） | SHAR-18 交付定义 |
| 团队 | 由多智能体小队开发；长期维护者是否熟悉前端框架**未知** | 假设，待确认 |
| 工程 | 全新空目录；是否 `git init` / 建远端仓库**待人工确认** | 父任务人工介入点 2 |
| 部署 | 是否上线、部署到哪**待人工确认**（涉及外部可见与花钱） | 父任务人工介入点 5 |

> **显式假设**（若假设不成立需重评本 ADR）：
> 1. 站点内容以静态展示为主，无服务端渲染的数据依赖（表单提交除外，单独决策）。
> 2. 部署目标为静态托管（Nginx / 对象存储 + CDN / Vercel / Netlify / GitHub Pages 之一），无 Node 常驻服务。
> 3. 不需要用户账户、个性化、A/B 实验等服务端能力。
> 4. 内容更新频率低（产品/证书偶发更新），不需要运行时 CMS 编辑界面。

## 3. 方案对比

### 3.1 候选方案说明

- **方案 A — 纯 HTML + 轻量构建（Vite）**：手写语义化 HTML，用 Vite 做资源打包/压缩/热更新，可选 TypeScript + PostCSS/Tailwind。无模板层、无组件层，页面即文件。
- **方案 B — 静态站点生成器（Astro 优先，11ty 备选）**：内容用 Markdown/JSON/YAML 数据源，用组件化模板（`.astro`）在**构建期**生成纯静态 HTML；默认零客户端 JS，交互点用「岛屿（Islands）」按需加载。
- **方案 C — 现代框架静态导出（Next.js 优先，Nuxt 备选）**：用 React/Vue 组件开发，`next export` / `nuxt generate` 产出静态 HTML；完整 SPA 路由与 hydration。

### 3.2 对比表

| 维度 | A. 纯 HTML + Vite | **B. SSG（Astro）** | C. 框架静态导出（Next/Nuxt） |
|---|---|---|---|
| 交付产物 | 静态 HTML（多文件） | 静态 HTML（构建期生成） | 静态 HTML + JS bundle（hydration） |
| 学习/上手成本 | 低（会 HTML 即可） | 中低（模板语法简单，接近 HTML） | 中高（需懂框架心智模型 + 构建配置） |
| 多语言适配 | 手工维护两套目录，易漂移 | **内置 i18n 路由 + 内容集合**，天然分区 | 需引入 i18n 库 + 路由改造 |
| 内容可维护性 | 差：改一处导航要改 ~60 个文件 | **好：数据/组件单一来源，改一处全局生效** | 好：组件 + 数据源 |
| 模板复用（列表/详情同构） | 差：12+ 详情页大量重复 HTML | **好：数据驱动循环生成** | 好 |
| 默认客户端 JS | 极少（仅自写交互） | **≈0（岛屿按需）** | 较大（框架运行时） |
| 首屏性能 / Core Web Vitals | 极好 | **极好** | 好（但需调优 hydration） |
| SEO（静态 HTML + 可控 head） | 好（但需手工管理每页 meta） | **好（组件化 meta + sitemap 集成）** | 好（但 head 管理更绕） |
| 视觉表现力（动画/设计自由度） | 高（无框架约束） | **高（原生 CSS/组件，支持任意动画）** | 高 |
| 交互组件（轮播/灯箱/搜索/表单） | 需自选库并手工接线 | **可复用任意前端库，岛屿隔离** | 生态最丰富 |
| 构建复杂度 / 配置面 | 最低 | 低（零配置起步） | 中高（配置多、陷阱多） |
| 依赖体量 / 供应链风险 | 最低 | 低 | 较高（框架 + 运行时） |
| 长期维护（换人接手） | 内容一改就痛苦 | **好（文档 + 数据源清晰）** | 好（但需框架知识） |
| 输出可移植性（不锁死平台） | 最高（纯文件） | **高（纯静态输出，可任意托管）** | 高（但倾向平台化） |
| 团队现有技能依赖 | 无 | 低 | 要求 React/Vue 能力 |
| 迁移/下线成本（回滚难度） | 低 | **低**（产物是纯 HTML） | 中（Java/JS 生态耦合） |

### 3.3 各方案的主要优势 / 劣势

**方案 A：纯 HTML + Vite**
- 优势：最简、零框架依赖、输出最可移植、任何人可接手；构建极轻。
- 劣势：**60+ 页面 ×2 语言全靠手写与手工同步**，导航/页脚/表单等公共区块会被复制几十遍；改一个菜单要改所有文件；双语漂移风险极高；模板同构的列表/详情页重复劳动巨大，与「内容完整、可核对」的验收要求冲突。

**方案 B：静态站点生成器（Astro）**
- 优势：**为内容站而生**——构建期生成纯 HTML（默认零 JS）、组件化复用（导航/页脚/卡片/表单一次编写）、原生 i18n 路由与内容集合、内置图片优化与 sitemap、岛屿架构按需加载交互、视觉自由度不受限（CSS/动画无限制）。输出纯静态、可托管于任意平台，回滚成本低。
- 劣势：引入一个**构建期框架**（有学习曲线，但语法接近 HTML，团队门槛低于 React/Vue）；团队若完全不熟悉需 0.5–1 天熟悉期；静态全量构建，内容极多时构建时间会增长（本项目规模下可忽略）。

**方案 C：现代框架静态导出（Next/Nuxt）**
- 优势：生态最丰富、组件能力最强；若未来要扩展为带服务端能力的应用（如接入 CMS、登录、实时数据）最顺滑。
- 劣势：对纯静态企业站是**过度工程**——为不需要的 SPA 路由/ hydration 付出体积与复杂度代价；配置陷阱多；要求团队具备 React/Vue 能力（未知）；调试与构建复杂度显著高于 A/B；与本项目「内容展示为主」的定位错配。

## 4. 推荐方案

**推荐：方案 B — 静态站点生成器，首选 Astro（11ty 为备选）。**

### 推荐理由

1. **与问题本质匹配**：项目是「内容驱动的双语静态企业站」，Astro 正是为此类场景设计——构建期出纯 HTML，零/极少客户端 JS，性能与 SEO 天然最优。
2. **直接解决盘点暴露的最大痛点**：60+ 页面、12+ 同构详情页、17 个二级分类 → 用**数据源 + 组件模板**生成，一次维护、全局生效，杜绝双语漂移与公共区块重复。
3. **多语言是一等公民**：原生 i18n 路由与内容集合，天然支持 `/zh`、`/en` 分区（详见 ADR-002），满足「每页双语、一一对应」的验收。
4. **视觉自由度高**：不受框架组件约束，可用任意 CSS/动画方案实现「先进、美观」，配合视觉验收。
5. **可移植、可回滚**：输出为纯静态文件，部署与下线都不锁死平台；即便未来换栈，产物仍是标准 HTML。
6. **团队门槛低于方案 C**：`.astro` 语法接近 HTML，非前端专家也能维护；交互点用岛屿按需增强，不必全站掌握框架。
7. **为未来留门**：若后续要接入 CMS 或增加服务端能力，Astro 支持 SSR/端点，不必推倒重来。

### 与「先进前端技术」的关系

选方案 B 不等于放弃先进技术：岛屿架构、内容集合、图片优化管线、TypeScript、现代 CSS、组件化、CDN/边缘静态分发——均为当代先进实践，且是**恰当使用**而非堆砌。这符合架构原则「用合适的技术解决合适的问题」。

> ⚠️ **待客户确认（升级条件触发）**：本推荐在「纯 HTML vs 引入框架/SSG」上做了**不可逆倾向的取舍**（引入构建期框架）。按父任务要求，此决策**不自行拍定**：现给出推荐与理由，标注 **「待客户确认」**，同时继续产出 ADR-002 与 architecture.md，使客户无论选 A/B/C 都能快速落地。若客户坚持「纯静态 HTML、零框架」，按 §6 回退到方案 A（目录与命令已预留）。

## 6. 回滚方式

**回滚目标**：若客户否决方案 B（或项目中途需放弃框架），应能以最小代价退回方案 A（纯 HTML + Vite）。

**为何回滚成本低**：
- 方案 B 的**产物本身就是标准静态 HTML/CSS/JS**，与方案 A 的产物形态一致。
- 目录结构、内容模型、页面划分原则（见 `docs/architecture.md`）对 A/B 通用，回退只需替换「构建与模板层」，内容与页面清单不动。

**回滚步骤（预案，非现在执行）**：
1. **保留内容源**：内容以语言无关的数据文件（JSON/YAML/Markdown）维护，不被框架特有语法污染。
2. **冻结框架层**：停止新增 `.astro` 组件；将已生成的静态产物直接作为方案 A 的起点。
3. **切换构建**：以 Vite 接管资源打包（`vite build`），模板区块改为 HTML 片段 + 简单 include（或用 11ty 作过渡）。
4. **验证**：`npm run build` 产出 `dist/`，`npm run preview` 本地核对页面与语言切换，通过视觉验收。
5. **记录**：写 ADR-003 记录本次回退决策（supersede 本 ADR）。

**不可逆性提示**：本项目不涉及数据迁移，回滚不产生数据风险；唯一沉没成本是已投入的框架化模板工作。因内容与结构均平台无关，回滚代价可控。

## 7. 决策摘要（TL;DR）

- **问题**：60+ 页面 ×2 语言的静态展示型双语企业站，用什么建？
- **结论**：推荐 **Astro（SSG）**；次选 11ty；若客户要零框架则用 **Vite + 纯 HTML**；Next/Nuxt 属过度工程。
- **理由**：内容驱动 + 强模板复用 + 双语一等公民 + 零 JS 性能 + 可移植可回滚。
- **状态**：**提议 + 待客户确认**（框架 vs 纯静态为不可逆倾向取舍）。
- **下一步**：客户确认技术栈 → 由开发按 `docs/architecture.md` 初始化工程（开发阶段执行）。
